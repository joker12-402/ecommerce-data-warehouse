# SQL 性能优化与指标准确性说明

本文档用于补充电商数仓项目中的 SQL 优化思路，重点关注大表 JOIN、COUNT DISTINCT 去重开销以及交易指标计算准确性问题。

## 1. 大表 JOIN 优化

在数仓开发中，大表 JOIN 容易带来性能问题，也可能因为关联粒度不一致导致指标计算错误。

常见优化方式：

- 分区裁剪：查询分区表时显式增加 `dt` 条件，避免全表扫描。
- 字段裁剪：JOIN 前只选择必要字段，避免 `SELECT *`。
- 先过滤再 JOIN：先过滤成功支付、成功退款等有效数据，减少 JOIN 输入量。
- 先聚合再 JOIN：对于一对多关系，先将多的一侧聚合到目标粒度，再进行关联。
- 小维表关联：大事实表 JOIN 小维表时，可考虑 MapJoin 或 Broadcast Join。
- 数据倾斜处理：对于热点 key，可通过过滤无效 key、热点 key 单独处理、加随机盐等方式优化。

## 2. 支付表与退款表关联优化

交易场景中，退款表可能存在一笔订单多次退款的情况。

如果支付表直接按照 `order_id` 和退款明细表 JOIN，可能出现一对多关联，导致支付金额被重复放大。

优化方式：

1. 先过滤支付成功、退款成功的数据；
2. 退款表先按照 `order_id` 聚合到订单粒度；
3. 再将订单粒度退款结果与支付表关联。

这样可以同时保证：

- 支付金额不会因为一对多 JOIN 被放大；
- JOIN 右表数据量减少；
- 支付金额、退款金额等指标口径更加清晰。

## 3. COUNT DISTINCT 优化

`COUNT DISTINCT` 通常需要全局去重，在大数据场景下会产生较大的 Shuffle 和内存开销。

优化方式：

- 去重前先做分区过滤、状态过滤和非空过滤；
- 在 DWS 层提前沉淀用户日粒度汇总表；
- ADS 层基于 DWS 汇总表统计用户数，减少反复从 DWD 明细层 `COUNT DISTINCT user_id`；
- 多个 `COUNT DISTINCT` 可以拆成多个子查询分别计算，再合并结果。

例如可以设计：

```text
dws_trade_user_1d
```

粒度为：

```text
dt + user_id
```

一行表示一个用户一天的交易行为。

ADS 层统计支付用户数时，可以基于该表直接统计满足条件的用户行数，而不是每次都从交易明细表中重新去重。

## 4. 精确去重与近似去重

对于用户数类指标，可以根据业务场景选择 Bitmap 或 HyperLogLog 等方案：

- Bitmap：精确去重；
- HyperLogLog：近似去重，适合超大规模 UV 估算。

但对于以下强准确指标，不能使用近似算法：

- 支付金额；
- 退款金额；
- 订单数；
- 结算金额；
- 财务类指标。

## 5. 本项目中的应用

本项目后续在交易数仓扩展中，可采用以下优化思路：

- 查询明细表时使用 `dt` 条件进行分区裁剪；
- JOIN 前进行字段裁剪，避免读取无关字段；
- 对退款表先按订单粒度聚合，再与支付表关联；
- 在 DWS 层建设用户日粒度汇总表，统一用户数统计口径；
- ADS 层尽量复用 DWS 汇总结果，减少重复计算。

## 6. 简历表达

可在简历中描述为：

> 优化交易指标计算 SQL：通过分区裁剪、字段裁剪、退款表订单粒度预聚合，避免一对多 JOIN 导致的指标放大；基于 DWS 用户日汇总表沉淀去重粒度，减少 ADS 层 COUNT DISTINCT 开销，提升交易日报计算效率与指标准确性。
